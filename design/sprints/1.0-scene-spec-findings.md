# What the real scene collection looks like

**Read from the live `PC` collection on 2026-09-20, before designing scene
specs.** Read-only: this was a listing, nothing was modified.

The plan's model for scene specs was written from three hardcoded names in
`obs_wire.py`. The actual collection is 11 scenes and 59 placements, and it
disagrees with the plan in one place, confirms it emphatically in another, and
settles a question the plan left open.

## 1. There are no groups. Every container is a nested scene.

59 placements: **49 `OBS_SOURCE_TYPE_INPUT`, 10 `OBS_SOURCE_TYPE_SCENE`**, and
zero groups.

`AI_AVATARS`, `Browser_Sources_Overlays`, `MERCH`, `chat-window`,
`DroidCam-w-Border`, `Queue-and-Border`, `GoPro-w-Border`, `OVERLAY_shop`,
`game-commercials-w-border` and `edge browser and border` are all scenes placed
inside other scenes.

This matches obs-websocket's own guidance -- *"Using groups is discouraged;
nested scenes are recommended"* -- and it means **the plan's group handling is
designing for something that is not here.** `GetGroupSceneItemList`, the
`flatten` opt-in, and `skipped: group_creation_unsupported` all exist to work
around the fact that groups cannot be created over the websocket. A nested scene
needs none of it: it is a source, placed like any other, and `CreateSceneItem`
already handles it.

**Consequence for 3a:** capture nested scenes as ordinary placements. Do not
build group support on spec. If a group turns up later, it will announce itself
as a placement that cannot be recreated, and that is the moment to decide.

## 2. Sharing is pervasive, not an edge case.

Eleven sources are placed in more than one scene:

| Source | Kind | Scenes |
|---|---|---|
| `AI_AVATARS` | scene | 5 |
| `Browser_Sources_Overlays` | scene | 5 |
| `BG_StreamOS-Cyber_Video` | input | 5 |
| `MUSIC` | input | 5 |
| `WhisperPy-Chat-Overlay` | input | 4 |
| `jurmiey_avatar` | input | 4 |
| `GAME`, `GoPro`, `MERCH`, `chat-window`, `OVERLAY_NowPlaying` | | 2-3 each |

The plan justified the layered source/placement model with one example
(`OVERLAY_NowPlaying` in two scenes). The real figure is eleven sources across
up to five scenes each, including the two nested scenes that carry most of the
overlay stack.

**Consequence for 3a:** a flat per-item model is not merely awkward, it would
corrupt this collection. Capturing `Game` and `Intermission` separately and
applying them back would write `BG_StreamOS-Cyber_Video`'s settings twice, with
whichever capture ran last winning. Sources and placements must be separate
top-level lists, and a settings write must happen once per source.

## 3. One source is placed twice in the same scene.

`jurmiey_avatar` appears in `Game` as **both scene item 245 and 259**.

This is the case FB-70's `source_name` resolution refuses rather than guessing
at, and it is live in the operator's collection rather than hypothetical. Any
spec addressing placements by source name would silently collapse those two into
one and lose a placement.

**Consequence for 3a:** a placement's identity is its scene item id, with the
source name as a reference. `SceneItemSpec` needs an occurrence index for the
case where one source appears more than once in a scene.

## 4. Scene item ids are per-scene, not global.

`id=1` occurs in `fullscreen capture`, `AI_AVATARS`, `Browser_Sources_Overlays`
and `Ending`. Ids are only meaningful with their scene, which the existing tool
signatures already assume -- worth stating because a spec that keyed on id alone
would look reasonable and be wrong.

## What to verify next, before writing the capture

- Whether a nested scene's transform round-trips like an input's (it should; it
  is a source), and whether `GetSceneItemTransform` behaves identically for one.
- What `GetSourceSettings` returns for a nested-scene placement -- a scene has
  no settings in the way an input does.
- Whether filters attach to nested scenes as they do to inputs.

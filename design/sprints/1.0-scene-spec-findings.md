# What the real scene collection looks like

**Read from the live `PC` collection on 2026-09-20, before designing scene
specs.** Read-only: this was a listing, nothing was modified.

> **Section 1 was rewritten on 2026-09-20 after a second read.** The first
> version said this collection has no groups, and it was wrong: it read
> `sourceType` and never checked `isGroup`, which is the only field that
> separates the two. Eight of the ten containers it named as nested scenes are
> groups. The corrected numbers are below; the error is described because it is
> the same mistake a capture would make.

The plan's model for scene specs was written from three hardcoded names in
`obs_wire.py`. The actual collection is **25 scenes and 104 placements across
two canvases**, and it disagrees with the plan in one place, confirms it
emphatically in another, and settles a question the plan left open.

## 1. Groups and nested scenes both exist, and look identical until you check

| Canvas | Scenes | Placements | Inputs | Nested scenes | Groups |
|---|---|---|---|---|---|
| Main | 11 | 85 | 65 | 10 | **10** |
| Aitum Vertical | 14 | 19 | 12 | 7 | 0 |

**Eight distinct groups, in ten placements.** `MERCH`, `chat-window`,
`DroidCam-w-Border`, `Queue-and-Border`, `GoPro-w-Border`, `OVERLAY_shop`,
`game-commercials-w-border` and `edge browser and border` are groups. Only
`AI_AVATARS`, `Browser_Sources_Overlays` and the nine top-level scenes embedded
in others are genuine nested scenes.

**The two are indistinguishable by the obvious field.** A group and a nested
scene both report `sourceType: OBS_SOURCE_TYPE_SCENE`, because "groups in OBS
are actually scenes, but renamed and modified" -- `GetGroupList`'s own
documentation. Only `isGroup` separates them, and getting it wrong is not a
cosmetic error, because **the two list calls refuse each other's arguments**:

- `GetSceneItemList` on a group: `602` *"The specified source is not a scene.
  (Is group)"*
- `GetGroupSceneItemList` on a scene: `602` *"The specified source is not a
  group. (Is scene)"*

Neither degrades, and neither is a superset, so a walker must dispatch on
`isGroup` rather than try one call and fall back. A group is also not an input
(`GetInputSettings` answers `602` *"The specified source is not an input."*) and
is absent from both `GetSceneList` and `GetInputList` -- so a capture that
enumerates scenes and inputs never sees one at all.

**So the plan's group handling is needed after all.** `GetGroupSceneItemList`
and `skipped: group_creation_unsupported` are load-bearing: obs-websocket has
`CreateScene` but **no `CreateGroup`**, so a spec can capture a group and can
never materialise a missing one. What survives from the first version of this
section is only the recommendation -- nested scenes *are* preferred -- not the
claim that this collection follows it.

FB-80 pins all of the above as contract rows. Note the live suite cannot create
its fixture: it borrows a group by duplicating an existing placement into the
scratch scene, and skips the group rows when a collection has none.

## 1b. A second canvas is enumerable, and its own flags do not say it is dead

`GetCanvasList` reports **Main** (2560x1440 @ 60) and **Aitum Vertical**. Every
scene-ish request takes an optional `canvasUuid`, and *omitting it means the
main canvas*, so `GetSceneList()` returns 11 scenes while the collection file
holds 25.

**The owner confirmed the Aitum Vertical canvas is disabled and its sources are
no longer needed** (2026-09-20). That settles the design question rather than
leaving it open:

> **A scene spec is scoped to the main canvas.** Omitting `canvasUuid` already
> does this, so the capture needs no canvas handling at all -- but it is now a
> decision with a reason behind it, rather than a default nobody examined.

What is worth keeping is the protocol behaviour, because it is a trap for
anything that later tries to be canvas-aware:

- **A disabled canvas still enumerates, and its flags still read as live.**
  Aitum Vertical reports `ACTIVATE: true`, `MIX_AUDIO: true`, `SCENE_REF: true`
  -- identical to Main apart from `MAIN: false`. So `canvasFlags` cannot be used
  to decide whether a canvas is doing anything.
- **Null dimensions are the actual tell.** Its `canvasVideoSettings` come back
  all-`null` while Main reports 2560x1440. A canvas with no dimensions cannot be
  laid out against, and that is the signal to skip one.
- **The dependency runs one way.** No vertical scene is placed inside a
  main-canvas scene; the vertical scenes pull in seven main scenes
  (`Game`, `Just Chatting`, `Ending`, `Desktop / Browsing`, `Intermission`,
  `League Queue`, `Starting Soon`). The vertical side is a leaf, so main-canvas
  work cannot disturb it and it cannot disturb main-canvas work.
- Four sources are used **only** by vertical scenes -- `CAM_16-9_border`,
  `NDI® Source`, `OBS Virtual Cam`, `PNGTuber`. They would be orphaned if those
  scenes were ever removed. Noted, not acted on.

`get_obs_status.video` (FB-69) and `internal/layout` describe the main canvas,
which is now simply correct rather than a silent limitation.

## 2. Sharing is pervasive, not an edge case.

Eleven sources are placed in more than one scene:

| Source | Kind | Scenes |
|---|---|---|
| `AI_AVATARS` | scene | 5 |
| `Browser_Sources_Overlays` | scene | 5 |
| `BG_StreamOS-Cyber_Video` | input | 5 |
| `MUSIC` | input | 5 |
| `WhisperPy-Chat-Overlay` | input | 4 |
| `jurmiey_avatar` | input | 4 |
| `GAME`, `GoPro`, `MERCH`, `chat-window`, `OVERLAY_NowPlaying` | | 2-3 each |

The plan justified the layered source/placement model with one example
(`OVERLAY_NowPlaying` in two scenes). The real figure is eleven sources across
up to five scenes each, including the two nested scenes that carry most of the
overlay stack.

**Consequence for 3a:** a flat per-item model is not merely awkward, it would
corrupt this collection. Capturing `Game` and `Intermission` separately and
applying them back would write `BG_StreamOS-Cyber_Video`'s settings twice, with
whichever capture ran last winning. Sources and placements must be separate
top-level lists, and a settings write must happen once per source.

## 3. One source is placed twice in the same scene.

`jurmiey_avatar` appears in `Game` as **both scene item 245 and 259**.

This is the case FB-70's `source_name` resolution refuses rather than guessing
at, and it is live in the operator's collection rather than hypothetical. Any
spec addressing placements by source name would silently collapse those two into
one and lose a placement.

**Consequence for 3a:** a placement's identity is its scene item id, with the
source name as a reference. `SceneItemSpec` needs an occurrence index for the
case where one source appears more than once in a scene.

## 4. Scene item ids are per-scene, not global.

`id=1` occurs in `fullscreen capture`, `AI_AVATARS`, `Browser_Sources_Overlays`
and `Ending`. Ids are only meaningful with their scene, which the existing tool
signatures already assume -- worth stating because a spec that keyed on id alone
would look reasonable and be wrong.

## 5. What a nested scene keeps from the input contract, and what it drops

The three open questions above were looked up before any code, then confirmed
against OBS 32.2.2. All four claims below are contract rows as of FB-79, so they
fail loudly if a future OBS disagrees rather than being comments that rot.

**libobs settles the general case in one sentence:** *"a scene is a source which
contains and renders other sources using specific transforms and/or filtering"*
(`docs/sphinx/reference-scenes.rst`), and `obs_scene_get_source` hands you the
`obs_source_t` to prove it. So the answer is not "scenes are a special case" but
"a scene is a source, and the input-shaped half of the protocol is the special
case".

| Question | Answer | Where it is written |
|---|---|---|
| Transform round-trip? | **Yes, identically** — including the FB-64 bounds normalisation. Neither `Get` nor `SetSceneItemTransform` names a source kind; they address `(scene, sceneItemId)`, and the transform belongs to the placement | protocol reference; row `a nested scene is placed and transformed like any other source` |
| Settings? | **No.** A scene is not an input and has none | `InvalidInputKind` (605) is *"the specified input (`obs_source_t-OBS_SOURCE_TYPE_INPUT`) had the wrong kind"*; a scene is `OBS_SOURCE_TYPE_SCENE` |
| Filters? | **Yes, identically.** `obs_source_filter_add` takes any `obs_source_t*`, which is why obs-websocket's filter requests take the generic `sourceName` and not `inputName` | `reference-sources.rst`; row `filters attach to a nested scene as they do to an input` |
| Can a scene contain itself? | **No.** `obs_source_add_active_child` returns *"false if it causes recursion"* | `reference-sources.rst`; row `a scene cannot be placed inside itself` |

**Consequences for the capture:**

1. `SourceSpec` branches on source type, and the branch is not cosmetic. A
   nested scene has no `kind` to re-create it from and no settings to store;
   it is a *reference* to a scene captured in its own right. Capturing scenes
   and inputs alike would produce a document that tries to re-create every
   container in the collection as an input.
2. **Filters must be captured for scenes too.** Ten of the eleven scenes are
   containers, so a capture that only walks inputs for filters silently drops
   filter state from almost the whole collection. This is the easiest of the
   four to get wrong, because it fails by omission and the document still looks
   complete.
3. The transform path is shared. There is no second code path for nested
   scenes, and `NormaliseBounds` covers them unchanged.
4. A cycle is a document error the applier will meet as a failed op, not a hang.
   4a can report it rather than guard against it.

**`obstest.Fake` could not express any of this** before FB-79 — `CreateSceneItem`
required `world.inputs[sourceName]`, so a nested scene could not be placed at
all, and filters resolved against inputs only. The fake could not model the
collection it stands in for, which is the same failure as `SceneSource.Visible`
in FB-60: a double that agrees with a test the real thing would refute. Worth
remembering when the next spec-shaped thing is designed against it.

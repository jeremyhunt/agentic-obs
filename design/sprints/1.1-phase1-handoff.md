## How to work on this

The three rules below were each learned the expensive way in the session that
produced this work. They are in priority order.

### 1. Look it up before writing a test about it

A test encodes an expectation. If the expectation is a guess, passing certifies
the guess. Four claims written confidently as comments were refuted by a live
run in one session:

- "obs-websocket applies the mute flag regardless of audio" — `InvalidResourceState (604)`
- "starting an already-running output is a no-op" — `OutputRunning`
- "OBS produces png, jpg or bmp" — this build reports **seventeen**
- "you cannot tell a missing vendor from a wrong request type" — the messages differ

**The tell is writing a sentence of the form "X does Y" about someone else's
system.** Stop there and look it up. The protocol reference gives a call's
*shape*; the *semantics* of values it passes through are in obs-studio; a
constant named in prose without a value is in the header. Expect to need more
than one tier: `/obsproject/obs-websocket` → `/obsproject/obs-studio` →
`libobs/*.h`.

A live run is not the research step. It only refutes what you happened to
exercise, and only after the wrong thing is committed.

This is written into the global `docs-first` skill, which loads automatically.

### 2. RED is per assertion, not per test function

Mutation testing caught three vacuous tests in one session, all with one cause:
no assertion-level RED.

- Added to an already-green test, passed immediately because a fixture already
  satisfied the weaker claim (FB-71: "places an existing input" would have
  certified a copy-instead-of-share bug as fixed)
- Satisfied by a leftover async notification (FB-66)
- Existed in a draft, silently dropped in a rewrite, so it never ran (FB-78)

So: **adding an assertion to a green test means breaking the thing it asserts
first** and watching that one assertion fail. **Rewriting a test file means
diffing the case list** before and after. Mutation stays as the backstop for
what escapes those, not as the mechanism.

### 3. Mutate the layer the test actually covers

Breaking `internal/obs` proves nothing about a test running against
`MockOBSClient`, which replaces that layer wholesale. This was violated again in
FB-69 — the canvas could be dropped from the status with no test noticing, and
two contract rows were needed to cover it.

**And verify the mutation applied.** A mutation that silently fails to apply
reads exactly like a test with no teeth. This went wrong twice: a PowerShell
helper called with a missing argument reported all four mutations uncaught (they
had never run), and CRLF-vs-`\n` patterns silently matched nothing. Use a script
that **fails loudly when the pattern is not found**.

### Verification, per increment

```sh
go clean -testcache                       # a cached pass has masked a real failure here
go build ./... && go vet ./... && go test ./...
go vet -tags obslive ./internal/obs/...   # the live suite must still compile
./scripts/verify-docs.sh && ./scripts/verify-skills.sh
```

Live suite, before a release — creates and removes a scratch scene **per row**
in the **active** collection:

```sh
OBS_LIVE_TEST=1 OBS_HOST=localhost OBS_PORT=4455 OBS_PASSWORD=… make test-live
```

Approved for the **`PC`** collection; check `%APPDATA%\obs-studio\global.ini`
key `SceneCollection` first, and confirm no `agentic-obs-*` scenes or inputs
remain afterwards.

## Things that cost real time to learn

**A transform read from OBS could not be written back.** OBS reports zero bounds
for any item that never had a bounding box; obs-websocket rejects a write below
1, even under `OBS_BOUNDS_NONE` where the value is inert; goobs marshals without
`omitempty` so the zeroes go on the wire. **OBS refused its own output**, and
every read-modify-write transform tool was broken on most items. `NormaliseBounds`
fixes it at the goobs boundary. The earlier handoff said the bounds rules were
"only survivable because every transform tool is read-modify-write" — that was
exactly backwards, and read-modify-write is what *triggers* it.

**`alignment` and `boundsAlignment` are different fields.** Alignment says which
point of the item sits at its position; bounds alignment says where the source
sits inside the box. And **`OBS_ALIGN_CENTER` is 0** — the absence of edge
flags, not a flag — so ORing it does nothing. Both are in
`internal/obs/alignment.go` with sources cited.

**Layout needs the canvas, never the source size.** OBS implements fit, fill and
stretch as bounds types, so a scale computed from source dimensions duplicates
OBS's work, divides by zero before a browser source loads, and goes stale when
the asset is replaced. `internal/layout`'s seven modes map one-to-one onto the
seven bounds types.

**The canvas here is 2560x1440.** The scene-designer skill assumed 1920x1080,
so every placement it computed was 640x360 out.

**A vendor probe is reliable.** Vendors cannot be enumerated, but the refusals
differ: *"No vendor was found by that name"* means absent, *"No request was
found by that name"* means present-but-wrong-request. Advanced Scene Switcher
and obs-browser are both installed here.

**goobs v1.8.3 panics on disconnect, and the live suite was provoking it.**
`client.go:351-368` checks whether `Disconnected` is closed and then sends on
`Opcodes`; `markDisconnected` closes both, so a server message arriving between
the check and the send is a send on a closed channel. It is a panic in goobs'
own goroutine, so it cannot be recovered from here — it fails the run. The
suite connected once per row and every row creates and removes scenes, inputs
and filters, so OBS was nearly always emitting an event as a row tore down.
Connecting once for the whole run instead of once per row took it from one
panic in four to six consecutive clean runs. It does not fix goobs, so a
*single* disconnect can still lose the race; if it ever reappears, the fix is
upstream, not another retry here. Row isolation was always a property of the
fixture — a fresh scratch scene per row — and never needed a socket of its own.

**The earlier notes still apply**: goobs marshals without `omitempty`;
`migrate()` forbids `ALTER TABLE`; `MockOBSClient` replaces the wire layer
rather than wrapping it; `-race` needs cgo; the live suite cannot gate CI.

## What is next

**3a — scene specs, read side.** `design/sprints/1.0-scene-spec-findings.md`
records what the live collection actually looks like, read before designing, and
it changes the plan in three ways:

1. **Groups and nested scenes both exist, and look the same until you check
   `isGroup`.** Eight groups in ten placements, alongside ten nested-scene
   placements, on the main canvas. *An earlier version of this list said there
   were no groups; that was wrong, and it was wrong because it read `sourceType`
   and never checked `isGroup` — which is exactly the mistake a capture makes.*
   Both report `OBS_SOURCE_TYPE_SCENE`, and the two list calls refuse each
   other's arguments with `602` rather than degrading, so the walker must
   dispatch. The plan's `GetGroupSceneItemList` and
   `skipped: group_creation_unsupported` are therefore load-bearing:
   obs-websocket has `CreateScene` and **no `CreateGroup`**, so a spec can
   capture a group and can never materialise a missing one. FB-80 pins this.
2. **Sharing is pervasive**: eleven sources across up to five scenes each, not
   the single `OVERLAY_NowPlaying` example the plan cited. A flat per-item model
   would corrupt this collection.
3. **`jurmiey_avatar` is placed twice in `Game`** (items 245 and 259), so a
   placement's identity is its scene item id with the source name as a
   reference, and `SceneItemSpec` needs an occurrence index.

**The three lookups are done (FB-79)** and their answers are in
`1.0-scene-spec-findings.md` §5, as a table with sources and as four contract
rows that now run against both the fake and OBS 32.2.2. In short: a nested scene
is placed, transformed and filtered exactly like any other source, because
libobs says *"a scene is a source"*; it is **not** an input, so it has no
settings and no kind to re-create it from; and it cannot contain itself.

Two of those bite the capture directly. `SourceSpec` must branch on source type
— a nested scene is a reference to a scene captured in its own right, not
something to re-create — and **filters must be captured for scenes as well as
inputs**, or filter state is silently dropped from ten of the eleven scenes.
That one fails by omission and still produces a document that looks complete,
which makes it the easiest of the four to get wrong.

So 3a starts at the capture itself. The remaining unknowns are shape decisions,
not behaviour: how a `SourceSpec` names a nested scene, and whether a capture
recurses into the scenes it references or captures one scene at a time and lets
the caller walk.

decision to take deliberately, not a detail to absorb into the capture. See
`1.0-scene-spec-findings.md` §1b.
